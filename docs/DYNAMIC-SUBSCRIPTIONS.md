# 动态额度 V2

本文件描述 V2 本地实现，尚未部署或启用生产订阅。开发日期为 2026-09-11，基线为 `1f80a587a`（`0.2.4-cyberaudit.7`），分支为 `feat/dynamic-quota-v2-20260911`。

站长已确认没有用户配置过 V1，因此只保留 V2，不提供版本切换、V1 策略迁移或双算法兼容。历史请求、计费去重、已承担记录和来源重置证据仍保留。

## 配置和分配

入口为「订阅管理 → 跟随上游动态额度」。默认关闭，管理员开启同样参与分配；关闭者不占份额，实际消费仍影响来源余量。

| 配置 | 规则 |
|---|---|
| 绑定上游 | 当前分组允许的直接授权 OpenAI OAuth 来源；保存后固定，不通过关开换源 |
| 分配上限 | 个人订阅本周期累计额度封顶，不是上游总容量上限 |
| 下调保护 | 必须显式填写，当前实现要求大于 0 且不超过分配上限 |
| 分配权重 | 正数，默认 1；按标准成本份额参与分配 |

下调保护提示统一为「仅用于自动调额，不承诺最低可用量。」不预填示例金额，也不把保护值当作额外余额。

首次开启实际按分配上限起步，保留已有用量。例如上限 $600、此前已用 $180，当前额度为 $600，个人未用为 $420，随后仍受本人在途占用、来源余量和原生日／月限制约束。没有足够来源数据时允许保存，显示「等待来源数据生效」；实际激活前继续按原规则执行。

自动调额以绑定来源本周期的 **10%、20%、30%……** 为节点。按原始百分比判断，19.96% 不算达到 20%；从 19% 到 32% 只按最新节点重算。同一来源、周期和节点在来源锁内原子发布，不因刷新、重复查询或重启重复发额。63% 中途加入不补跑历史节点，等待 70% 和有效学习样本。

分配按累计消费和权重计算，在个人下调保护与分配上限之间分配，封顶后的余量继续分给未封顶者。删除 V1 的 80%／20% 分配、个人 $5／$10 上调门槛、每 30 分钟上调及首次容量人工批准。

- 修改上限／下调保护，立即将本人的当前额度约束到新范围，不重分其他人的额度。
- 权重和成员变化在下一有效 10% 节点统一计算。
- 重复保存或关闭再开启保留已用量和已分配标准份额，不重新领取一次分配上限。
- 已用超过新额度时，剩余为 0，不清消费、不退款。
- 只有确认绑定上游真正重置，才为该来源有效开启的订阅开始新周期，并重新按分配上限起步。

下调保护合计超过可信预算时，保留原分配并向管理员提示冲突。来源保护仍决定实际可用量，不能为了满足显示额度而突破上游限制。

## 容量学习与官方保护

来源学习、份额及异常风险按标准费用计算；用户额度、已用和补扣金额按实际计费金额展示。倍率变化不重算历史账单；已发布的用户额度不会随页面刷新或每条账单变化。

只使用同一上游身份、同一 7d 维度、同一确认周期的实际费用增量：

```text
区间总容量估算 = 实际标准费用增量 ÷ (上游已用百分点增量 / 100)
```

当前本地验证参数为：区间至少 10 个百分点且至少间隔 1 分钟；乘 0.9 作为保守系数；最近最多 3 个样本取中位值（偶数时取较低值）。相对可信容量偏离超过 20% 时，需要 3 个独立区间在 5% 范围内一致。反复查询相同百分比不是新样本。

这些是开发验证参数，尚未进行脱敏历史回放校准，不应当作已确认的生产策略。估算不是官方承诺的美元周额度；异步计量、模型配比、价格和站外消费都会影响准确度。

异常样本不直接改写可信容量或个人额度。已有可信周期内，查询失败／估算暂缓仍可在已知预算内使用，扣除后来消费和来源风险占用；不能靠异常的 $9,000 估算为耗尽用户补额。缺少可信基线、身份改变、周期待确认或旧周期边界已过时，拒绝无法安全判断的新请求，在途结算继续。

百分比保护统一复用官方账号／全局 7d 自动暂停阈值：账号正值覆盖全局，留空／零继承全局，明确禁用则不使用该窗口阈值。5h 官方调度保护保持原样。来源保护不等待 10% 分配节点；由于在途消费和上游计量延迟，不能保证精确停在 98.000%。

卡片、列表和详情只读本地状态；复用现有额度元数据后台同步，不添加模型探活，也不改变渠道探活频率。重置验证仍需要独立新鲜的元数据证据。

## 保存、在途和结算

保存只做身份／分组／参数／版本校验及事务持久化，不同步等待上游网络或旧账恢复。来源被移出分组或授权失效后，仍允许关闭已有合法绑定。

同一来源锁协调保存、准入、分配、结算及重置。每条 HTTP 请求／每轮 WS 固定用户、订阅、来源和周期。开启前的请求也保留归属，后续真实结算更新其归属订阅的持久周期用量。原有周计时和普通手动重置不能清空已生效动态周期。

新请求和 WS 每轮都检查生效规则，不只在建连接时检查。适用范围仍为正常计费模式下的文本 Responses（含 compact、WS）、Chat Completions、Messages；Simple 模式及未接入原子计费的跨平台／图片／音视频入口不在此范围。

计费沿用冻结定价凭证、原有事务和 live／archive 去重。真实用量不按预占估价，迟到结果不换用户或周期。健康长请求续租，不因运行超过五分钟误判为免单。HTTP／WS 断连保留已取得的本轮用量，不把前一轮累计量再扣一次。

## 异常账务

正常结算失败时先做有界恢复。已计费记录只核对状态／缓存，不重复扣款。请求结束或确认失联约五分钟后，仍未结案的受管订阅请求再进行异常分类；配置保存不受分类结果阻塞。

| 当前本地参数 | 行为 |
|---|---|
| 单笔标准费用小于 $5 | 凭证完整、归属匹配、累计未达门槛时可自动由站点承担 |
| 同来源同周期累计达到 $20 | 后续异常进入复核，已承担记录不翻案 |
| 未知金额累计 5 笔 | 触发一次来源周期告警；未知金额始终进入复核，不按零或预占自动免单 |
| 余额账单或订阅归属不匹配 | 不适用小额订阅自动承担，进入复核 |

金额和样本参数为开发默认值，需投产前确定；本轮没有按这些规则处理真实账单。自动分类只处理有固定归属和执行状态的受管请求，不猜测旧记录归属。

「订阅管理」刷新按钮左侧显示「待复核」和「站点承担」笔数及已确认金额，未知笔数单列。汇总覆盖当前筛选全部记录，不只当前分页；明细以邮箱识别用户，并分当前周期和历史归档。

人工补扣只使用完整、匹配的原订阅凭证，展示用户实际计费金额；事务重新验证当前状态、原周期和原生计费窗口。未知金额不能按预占补扣，余额账务不从此入口重放。补扣沿用原子计费和去重；处理租约及唯一领取标识阻止重复点击、并发管理员、过期工作进程重复收费。

站点承担显示「已处理 · 站点承担」，不可核实金额另行注明。承担后不再追扣、不退款、不阻塞个人配置；迟到凭证只能补充实际承担金额。异常不再冒充个人活跃在途，但来源保留必要风险预留。已确认费用取代估计风险，已扣过的记录不增加站点损失；原预占保留作参考，不篡改成实际账单。

只在独立确认对应来源重置后，旧周期异常结案归档，不把旧债扣到新周期。#4 重置不操作 #5；未开启者的原生周用量、日／月消费、余额和历史统计不跟随清零。跨周期仍运行的请求只保留必要执行保护。

## 界面与通知

用户卡片突出剩余，分别显示个人用量和上游下次调额节点；详情显示最近实际变更的前后金额、原因、周期起点及同步／重置时间。最近同步不冒充最近调额。管理员列表用紧凑卡片；配置和账务分别展开。

保存成功保留窗口、显示服务器确认值和版本；刷新不覆盖未保存编辑。网络超时或服务端 5xx 后仅回读一次核对版本和字段，不盲目重复写入；不能确认时保留输入并提示待核对。

普通用户只能读取自己的订阅信息，隐藏来源身份、容量样本和管理员诊断；账务查询和处理走管理员鉴权。金额、参数及 JSON 大小／字段继续校验。

独立 TG 监控脚本已有本地配套修改：同一来源周期只发一次累计账务升级提醒；发送预算冲突、保护状态变化和重置结果，不逐笔推送小额自动承担。通知不含提示词、回复、密钥或完整凭证。脚本仍在管理目录单独维护，尚未部署，未发送真实 TG 消息。

## 数据库与验证

新增迁移 `240_dynamic_quota_v2.sql`：下调保护、持久周期用量、待激活状态、最近真实调额及复核信息；删除旧上调门槛列。迁移 238／239 不改写。停用或已撤销订阅的遗留配置保持原样，不编造下调保护值、不自动开启；首次显式填写 V2 配置时按分配上限起步并保留已用。若存在开启中且缺少下调保护的策略，迁移失败而不是静默改额。迁移本身不扣费、不退款、不清历史。

本地验证使用独立 PostgreSQL 17 临时实例、专用测试库和合成数据；未接生产数据库、未请求付费模型。主要回归命令：

```bash
# SUB2API_MODEL_QUOTA_TEST_DSN 必须指向独立测试库 sub2api_modelquota_test。
go test -race ./internal/service ./internal/handler ./internal/handler/admin ./internal/repository \
  -run 'Test.*(DynamicQuota|Subscription|UsageBilling|ModelRequestQuota|ModelQuota|Cyber)' -count=1
go test -race ./internal/server/routes -run TestDynamicQuota -count=1
go test ./internal/server/routes ./migrations -run '^$'
```

前端复用 Vitest 验证配置保存、卡片、异常明细、管理员列表与双语键完整性，并运行改动文件 ESLint 和 `pnpm run build`（包含 Vue 类型检查）。TG 运行既有 `--self-test`。

关键场景包括：初始保留消费、关开不补额、异常容量不救活耗尽用户、跨来源重置隔离、重复节点、待复核不阻塞保存、真实长请求、迟到结算、并发处理、旧领取者隔离、余额／归属校验、迁移重复执行和管理员路由保护。

开发回归不等于发布验收：仍需金额策略确认、脱敏历史采样校准、真实窄屏／深色页面目视验收和独立发布／恢复验证。本轮没有生产改额、历史清账、发布、提交或推送。

回退不能通过恢复旧业务数据库丢弃真实消费。启用 V2 后也不能直接运行不理解其分配和账务状态的旧二进制；实际发布须选用匹配的验证产物和恢复方案，主备一致。
