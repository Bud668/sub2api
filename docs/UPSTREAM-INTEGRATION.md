# 修改版主线与官方更新接入规范

2026-09-09 起执行：**自有源码主线开发 → 评估官方更新及依赖 → 受控合入 → 回归、构建与备份 → 主备同一产物**。

## 源码管理

- `main` 是自有产品主线；功能、修复和发布维护分别提交，发布使用固定标签与完整源码提交，不仅保存一个不断扩大的累计补丁。
- `upstream` 指向 `https://github.com/Wei-Shaw/sub2api.git`。保留官方 tag/commit 和原始历史；不改写已发布标签，不强推覆盖公开历史。
- 从功能分支提交变更；上线依据已验收的固定提交，不自动部署 main 或 latest。历史累计补丁仅作审计/过渡材料，不再作为新功能的主要开发入口。
- 官方有满足需求的等价实现时，评估替换自有实现，并保留能证明边界行为的回归用例。

## 更新分类

| 官方变更 | 处理要求 |
|---|---|
| 安全、鉴权、隐私、越权、凭据保护 | 优先评估适用性；适用时及时修复，不能仅以“功能用不到”跳过 |
| 计费、额度、数据一致性、核心 HTTP/WS 协议 | 检查完整调用链、依赖提交和迁移，回归后接入 |
| 可选平台、界面、新功能 | 按实际需求选择；可以不跟，记录原因 |
| 大型重构、依赖升级、破坏性迁移 | 单独评估，必要时批量合并稳定基线，不能只摘表面一行修复 |

每次准备发行都检查官方更新和安全通告，至少每月复核一次累计差异；严重安全通告优先处理，不等功能版本。定期与较新的官方稳定基线对齐，避免无限期冻结旧内核。选择性合入并不天然更省维护成本。

每个官方版本在 [接入台账](UPSTREAM-LEDGER.md) 记录：来源提交、采用/暂缓/不适用、理由、依赖、迁移、对应自有提交与测试。尚未评估必须明确标注，不等同于不适用。

## 发布门槛

1. 评审源码差异、敏感信息和许可证；核对依赖锁文件、数据库迁移与回退兼容性。
2. 从固定提交执行 `tools/build-managed-release.sh`。认证缓存删除队列测试、停用后所有 Key 拒绝、HTTP/WS 首帧/续轮额度、北京时间零点、错误归类、审计脱敏与前端交互均须回归。
3. 核验二进制版本、源码提交和 SHA-256；验收清单注明测试结果。失败不自动重试到变绿，不删除或弱化失败用例。
4. 部署前加密备份配置与数据库，保留旧产物；检查安全写入失败停转锁，不能通过重启清除尚未处理的安全状态。按维护窗口处理在途连接。
5. 同一产物分发主备；先验备机文件且保持不接入，再受控切换主机。不得自动覆盖业务库、清空计数、安全状态或 TG 游标。
6. 验证健康、未登录权限边界、前端资源和自然业务；发布精确标签、说明、源码、二进制与校验值。公开附件不包含内部备份、操作日志或生产配置。

发布自动化不拥有生产 SSH/数据库凭据。仓库 CI 可测试，但不自动上线或直接生成 latest 覆盖经过验收的产物。独立通知/部署组件保留自己的版本与验收记录。
